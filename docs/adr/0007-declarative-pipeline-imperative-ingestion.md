# ADR-0007 — Declarative pipeline for transformation, imperative job for ingestion

- **Status:** Accepted
- **Date:** 2026-10-09

## Context

Two kinds of work exist in this platform, and they have opposite shapes.

Fetching from the Riot API is stateful, imperative I/O: a token bucket for the rate limit,
pagination, exponential backoff on HTTP 429, a controlled exit on HTTP 403, and a
deterministic skip for responses already on disk.

Everything after the landing zone is a set of table definitions with dependencies between
them, incremental processing requirements, quality rules and lineage.

## Decision

Split by nature of the work.

```
Job  ingest_and_transform_challenger        (weekly)
├── task  fetch_riot_challenger             Python wheel task, imperative
│         RiotClient + TokenManager → landing volume
└── task  transform_medallion               pipeline task
          triggers the declarative pipeline

Pipeline  transform_lol_medallion
          landing → bronze → harmonized → consumption
          dependency order inferred; expectations native; lineage automatic
```

There is **no job for each layer transition.** `harmonized → consumption` is an internal edge
of the pipeline, inferred from which tables each definition reads. Orchestrating it by hand
would discard the main benefit of the declarative model.

Pipeline code is generated by iterating a registry, so there is one pipeline file per layer
rather than one per entity. All logic lives in plain classes and pure functions; the decorated
functions contain a single call. See [code architecture](../architecture/code-architecture.md).

## Alternatives considered

**All PySpark in Jobs.** Full control, trivially unit testable, no exposure to the Free
Edition pipeline limit. Rejected: expectations with per-rule failure counts, incremental
streaming tables, dependency resolution and lineage would all be hand-written, and that
plumbing is both the least interesting code in the project and the most likely to contain
bugs. It would also omit the Databricks capability most frequently named in job descriptions.

**All in a declarative pipeline.** Rejected as technically impossible: a declarative pipeline
cannot perform throttled, retrying, stateful HTTP I/O against a third party, and should not
try.

**A separate job per layer transition.** Rejected: it re-implements dependency resolution that
the pipeline performs correctly, and consumes the limited concurrent-task budget.

## Consequences

- Two paradigms coexist in one repository and must both be explained. This is a documentation
  cost, paid in the code architecture page.
- Logic inside a `@dlt`-decorated function would be untestable, because `dlt` exists only in
  the pipeline runtime. This forces a structure that is independently good: pure
  transformation functions, thin declarative shells, and unit tests that need no Databricks.
- Expectation definitions live as class attributes next to the transform that produces the
  columns they check, so they cannot drift into a separate config file.
- **Open risk:** one active Lakeflow pipeline per type on Free Edition may prevent dev and
  prod pipelines from coexisting. See [ADR-0002](0002-single-workspace-two-bundle-targets.md)
  and the [validation plan](../operations/validation-plan.md).
